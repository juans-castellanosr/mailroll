# mailroll

## 0.2.0

### Minor Changes

- 89a4319: The send history moves to a new format, records evidence for tracing, and reports rejected CC addresses. This is a breaking change:

  - **One-way history upgrade.** The first live run that writes to a list upgrades its history to v2. The old snapshot is copied to `<stem>.json.v1-backup` and the old journal is moved to `<stem>.jsonl.v1-backup`; neither is ever overwritten. Afterwards, mailroll 0.1 refuses the list with `invalid state file`. Dry runs, test sends and `status` never upgrade; they say that the next live run will. An interrupted upgrade is finished by the next live run. The new format needs a file system with hard links. Going back to 0.1 means restoring the backups by hand, which is only safe if 0.2 never attempted a send to that list. The file-system behavior has not been verified on Windows or macOS yet.
  - **Evidence.** The history keeps `attemptId` (one per send intent, the same across its retries), `providerMessageId` when the integration returns one, `cc` (rejected CC addresses and whether a CC was required when the message was sent) and `uncertainAttemptIds` (earlier attempts that ended uncertain). It is for tracing only: `sent` still means accepted by the provider, never delivered.
  - **Rejected CC.** A message the provider accepted is never sent again because its CC was rejected. With `"ccPolicy": "required"` the run needs attention, so `needsAttention` is `true` and the CLI exits with `1`; a rejected optional CC alone does not change the exit code. The run summary and `status` count messages with a rejected CC, `send --json` adds `ccRejected`, `history` and the attention status `cc-rejected`, and `status --json` adds `history` and `evidence`.
  - **SDK types.** `TemplateState` is v2, `StateStore.load` returns `StoredTemplateState` (v1 or v2), and `compact` receives a v2 state. New exports are `upgradeTemplateState`, `foldJournal`, `StoredTemplateState`, `TemplateStateV1`, `CcObservation`, and the types `RunHistory` and `HistoryPresence` from `mailroll`. `RunReport` gains `ccRejectedMessages` and `requiredCcRejectedMessages`, `TemplateRunResult` gains `history`, `ListCounts` gains both CC counts, and `ListReport` gains `evidence`. Code that builds these values or implements a `StateStore` must be updated; see the migration guide.
  - **Other changes.** A snapshot's `updatedAt` is the `at` of the last recorded recipient entry, not the time the snapshot was written. An intent superseded by a later released intent now reads as uncertain instead of being dropped. A custom `newAttemptId` must return a new, non-empty id for every send.

- 89a4319: Outlook is now an optional package, `@mailroll/outlook`, activated like any other integration. This is a breaking change for anyone who sent through Outlook:

  - Install it next to mailroll and declare it: `npm install @mailroll/outlook` and `{ "integrations": ["@mailroll/outlook"] }` in `mailroll.json`. mailroll includes no integration, so without the declaration every run, dry runs included, refuses Outlook connections.
  - `mailroll export-sent` became `mailroll-outlook export-sent`, from `@mailroll/outlook`, with the same options, output file and exit codes.
  - The Outlook exports moved from `mailroll` to `@mailroll/outlook`: `outlookIntegration` (now also the default export), `createOutlookIntegration`, `GraphClient`, `OutlookAuthProvider`, `OutlookProviderFactory`, `SentItemsReader` and their types.
  - `runSelection` activates no integration by default; pass `integrations: [outlook]`.
  - New in `mailroll`: `connectionStateLocation`, the state folder and key a connection's integration receives.

  Connections keep `"kind": "outlook"`, the secrets keep their variable names, and the token cache and send history stay where they are, with no new sign-in.

- 89a4319: List locks identify their owner and recover stale locks one run at a time:

  - **Token.** The lock file `<stem>.json.lock` now holds `{"pid", "host", "startedAt", "token"}`, where `token` is a random id per lock. A run releases its lock only while the file is still the one it created and holds its token, so it never deletes another run's lock. Locks written before the token existed are still read, but no longer recovered automatically, because they do not record their process space; see the process-space change.
  - **Serialized recovery.** A lock left by a process that mailroll can prove is no longer running (same host name, same process space) is recovered under a `<stem>.json.lock.recover` marker. The stale lock is moved aside to `<stem>.json.lock.stale-<id>` and removed only if the moved file is still the same file and holds the same owner, so a replacement that took the deleted lock's inode number is never removed, and the new lock is created in its place. A run that finds a recovery in progress stops with `… is being recovered by another run (…); try again when it finishes …`. A marker left by a run that ended during a recovery is never removed automatically: the next live run stops with `… cannot be recovered: an earlier recovery of … did not finish and left ….recover (…)`, and tells you to delete it once no run and no recovery is active on any machine that shares the folder. A recovery that cannot finish safely deletes nothing and stops, either with `… could not be taken: the lock left by …, which is no longer running, kept changing while mailroll tried to recover it; try again`, or with `the lock … was replaced while it was being recovered, which only happens if someone deleted it by hand during the recovery; nothing was deleted: …`.
  - **New message.** The message for a lock in use is now `… is in use by another run (…). Wait for it to finish; if no run and no lock recovery is active on this list (<path>.recover does not exist), delete <path>`.
  - **Leftovers.** A crash or kill can leave `.tmp`, `.stale-<id>` or `.recover` files next to the lock. The first two are never read; the third blocks the list until it is deleted.
  - **Hard links.** Locks are now created atomically, with a temporary file and a hard link. On a file system without hard links, every live run stops before sending anything with `could not create <path>; nothing was left behind`. There is no fallback. This has not been verified on Windows or macOS yet.

- 89a4319: When a list's history cannot be written, the error and the logs say which write failed and what it means for the recipient:

  - **Messages by stage.** `StatePersistenceError` still starts with `could not record send state`, now followed by what failed and the cause from the file system:
    - intent: `could not record send state before sending to <address>; this run did not call the provider for it, though the history may read this attempt as uncertain: <cause>`
    - outcome: `could not record send state after sending to <address>; the history will read this attempt as uncertain, so check whether it was delivered before resending: <cause>`
    - release: `could not record send state after the send to <address> stopped without the provider accepting it (it may not have been called); the history will read this attempt as uncertain: <cause>`
    - snapshot: `could not record send state snapshot; no recorded outcome is lost, and the next live run replays the journal: <cause>`
  - **`recipient.unrecorded` event.** An `error` log event for each recipient whose intent, outcome or release could not be written, with `templateId`, `connectionId`, `email`, `attemptId` when there is one, `stage` and `error`. A failed snapshot has no such event. With several connections, the event and the error of a recipient on another connection can carry the cause of the write that failed first.
  - **Flush events.** `state.journal_kept` now has the reason `an intent is still open`, and is logged when intents are still open after a failed write. `state.flush_failed` is logged only when writing the snapshot fails after the list already stopped on an error. Flushing no longer throws the error that was already reported; what is on disk, the error the caller receives and the recovery on the next run do not change.

  No public API changes: `StatePersistenceError` has the same fields.

- 89a4319: A list's history can only be written by the run that holds its lock. This is a breaking change for code that calls `FileStateStore` directly:

  - **Writes need the lock.** `FileStateStore` refuses `append` and `compact` with `ConfigError`, and writes nothing, unless the same instance took the list's lock with `lock()` and loaded the list after taking it. Before each write it checks that the lock file still belongs to this run, so a run whose lock was deleted, taken over by another run or became unreadable stops writing. The message is `the send state of "…" · … can only be written by the store that holds its lock and loaded it after taking it (…); nothing was written`, with the reason in parentheses. Call `lock()`, run the list with `runTemplate`, which loads it, and call `release()` on the lock in a `finally` block. The CLI and `runSelection` already do this. Writes to one list are now serialized within a store.
  - **One live run per list and store.** `runTemplate` refuses a second live run of the same list on the same `StateStore` instance while the first is running, with `… is already used by another live run of this state store; nothing was sent`. This applies to every store, `MemoryStateStore` included.
  - **Known limit.** If someone deletes the lock of a live run by hand and starts another run on the same list, the ownership checks narrow but do not remove the chance that messages are sent twice: a suspended run that overwrites the history can erase every send the other run recorded, and a later run resends all of them; see the limits in the changeset about runs that lose their lock while they write.

### Patch Changes

- 89a4319: On Linux, a lock is no longer recovered from a run in another container that has the same host name. Until now mailroll treated a lock as abandoned when it was taken on a machine with the same host name and its process id did not exist, so a run in one container could take over the live lock of a run in another container that shares the state folder, and both would send to the same list.

  - **Process space.** The lock file and the `.recover` file now also hold `pidSpace`, the process space of the run. On Linux it is the kernel's boot id and the identity of the run's PID namespace, and it is left out when either cannot be read. On macOS and Windows it is the platform and the host name, which adds nothing to the host name: there, two machines with the same host name that share a folder, cloned virtual machines, or Windows containers with process isolation can still take over each other's live lock. Give each of them its own host name. Other platforms record no process space.
  - **Recovery only when provable.** mailroll recovers a lock only when it has the same host name, the same process space and no process with its id. Otherwise the run stops before sending with `… is in use by another run (…), and mailroll cannot tell whether that process is still running: <reason>`, or, for a `.recover` file, with `… cannot be recovered: <path>.recover shows that … is recovering <path> or stopped while doing so, and mailroll cannot tell whether that process is still running: <reason>`. The reason names the boot ids or PID namespaces that differ, and the message says what to check before deleting the file by hand.
  - **Stale locks you now delete by hand.** A stale lock is no longer recovered automatically when it was left before a restart of the machine, by a container that has been restarted or removed since, by mailroll 0.1, which writes no `pidSpace`, by a run that could not read its own process space, or on a platform other than Linux, macOS or Windows. Delete it once you are sure its run has ended.
  - **Every run must be upgraded.** A run of mailroll 0.1 that shares the folder still recovers locks by host name and process id alone, so the protection holds only once every run that shares the folder uses this version.
  - **Not verified in user-space kernels.** Sandboxes such as gVisor report their own `/proc`; whether they give each sandbox its own boot id and PID namespace identity has not been verified.
  - **A lock is bound to its file.** A run holds its lock only while the lock file is the very file it created. A copy put back by a sync tool or a restored backup, even with the same content, no longer counts as the run's lock, so the run stops writing instead of writing next to another run, unless the file system happens to give the copy the inode number the original had, which some file systems, such as ext4 and tmpfs, reuse once a file is deleted.
  - **Release never deletes or restores another run's lock.** A run releases its lock by moving it aside to `<stem>.json.lock.stale-<id>`, checking that the moved file is its own, and removing it. If the lock was deleted by hand and another run created its own between the check and the removal, the moved file is never put back, because a third run may have taken and used the list in the meantime: it stays as `<stem>.json.lock.stale-<id>`, the release fails with `<path> was replaced while this run was releasing its own lock, which only happens if someone deleted it by hand; nothing was deleted: the replacement is kept as <copy>, and the run whose lock it is will stop at its next check. …`, and that run stops at its next check. A recovery that finds the same kind of replacement does the same, with `the lock <path> was replaced while it was being recovered, …`; until now it put the replacement back. If the moved copy cannot be removed, the release fails with `<path> was released, but the copy it was moved to, <copy>, could not be removed; mailroll never reads it, and it is safe to delete`.

- 89a4319: A live run whose lock file is deleted while it writes the list's history no longer lets a message go out twice in the cases that could be reproduced, and no longer erases what the run that took the list over has written:

  - **Intents.** Before, the run checked that it still owned the lock and then wrote the send intent; if the lock was deleted between the two and another run took the list, both runs could send the same message. The run now checks the lock again after writing each intent and before calling the provider. If the lock was lost meanwhile, the run does not send that message and stops with a `StatePersistenceError` at the `before sending to <address>` stage, whose cause reads `the intent to send to <address> was written to the send state of "<template>" · <file.csv>, but right after it this run could no longer confirm that it holds its lock (<reason>); nothing was sent to <address>, and the history now reads it as uncertain`. The other run reads that recipient as uncertain and does not send it by itself. The history shows it with the message `the run ended before the outcome of this send was recorded (crash, kill or power loss)`, although the provider was not called.
  - **Snapshot, journal and upgrade.** Before, a run that lost its lock could still finish writing its snapshot and delete the journal, cut off a torn last journal line, or upgrade a v1 history, erasing the records of the run that took the list over, which a later run then sent again. The run now checks the lock right before each step that replaces, shortens or deletes a history file, and stops without it. The causes read `the send state of "<template>" · <file.csv> can only be written by the store that holds its lock, and while preparing the history files this run could no longer confirm that it holds it (<reason>); it stopped before changing them further`, and, when the snapshot was already written, `the snapshot of the send state of "<template>" · <file.csv> was written, but right after it this run could no longer confirm that it holds its lock (<reason>); the journal was kept, so no record written by another run was removed`.

  Limits: this is not exactly-once delivery.

  - Each check and the step it protects are separate file-system calls. A run suspended by the operating system between the two, for as long as another run takes the list, sends and writes its history, can still overwrite that history, which erases every send the other run recorded, so a later `pending` run sends them all again. The same goes for a journal line it was already appending. For example, a late `failed` outcome written after the other run was deliberately told to resend that recipient (`subset` or `force-all`) and recorded `sent` is read last, and a `failed-only` run then sends the message again, unless the other run wrote its snapshot after that line.
  - The checks treat the lock as the run's own only while the lock file holds its token and is the same file (device and file number). A deleted lock that comes back, restored by hand or by a sync tool, fails the check unless the file system gives the copy the file number of the deleted file, which file systems can do.
  - When the lock file cannot be read (for example `EMFILE`, `EIO` or `ESTALE`), the run stops as if it had lost the lock, and says that nothing was sent to the recipient; the lock may in fact still be its own.
  - The checks rely on every run seeing, at once, the files another process has just written. That holds on local disks and is likely on NFS. It is not established on SMB shares, Windows folders opened from WSL, or folders synced by iCloud, OneDrive, Dropbox or Syncthing.
  - A run of an earlier mailroll that shares the folder makes none of these checks, so mixing versions on one list keeps the old risk.
  - A program that runs `runTemplate` with its own state store that takes no lock gets none of this protection.
  - A send that times out at the provider stays uncertain.

- 89a4319: On Windows, writing the send state no longer fails because a folder cannot be flushed to disk. Windows does not let Node.js flush a folder, and the flush is refused with `EPERM`. On Windows mailroll now skips that flush when it is refused with `EPERM`; any other error, including one from opening the folder, still stops the write, and other platforms still flush the folder as before. On Windows the creation, renaming or removal of a state file is therefore not flushed explicitly: a journaling file system such as NTFS keeps the folder consistent after a crash, but the latest such change may be lost on power failure, and on a network share it depends on the server. This has not been verified on Windows yet.

## 0.1.0

First public release.

- CLI `mailroll`: guided menu, `send` (dry-run, test inbox, live), `status`, `build-template`, `export-sent`;
  JSON output, documented exit codes, orderly Ctrl-C.
- Node SDK `mailroll` and browser-safe `mailroll/core`.
- Per-list send history with intents, uncertain outcomes and safe resend policies.
- Microsoft Graph (Outlook) provider with delegated device-code sign-in.
- One set of email address rules everywhere: recipients, CC, test inboxes and connection mailboxes. Length limits are measured in UTF-8 bytes.
- `buildSelection`, `runSelection` and `runTemplate` validate addresses at runtime, so values from untyped callers are rejected with a `ConfigError` naming the field instead of being sent unchecked.
- A connection's `mailbox` accepts the same addresses as recipients, including internationalized ones and surrounding spaces, which are trimmed.
