A live run whose lock file is deleted while it writes the list's history no longer lets a message go out twice in the cases that could be reproduced, and no longer erases what the run that took the list over has written:

- **Intents.** Before, the run checked that it still owned the lock and then wrote the send intent; if the lock was deleted between the two and another run took the list, both runs could send the same message. The run now checks the lock again after writing each intent and before calling the provider. If the lock was lost meanwhile, the run does not send that message and stops with a `StatePersistenceError` at the `before sending to <address>` stage, whose cause reads `the intent to send to <address> was written to the send state of "<template>" · <file.csv>, but right after it this run could no longer confirm that it holds its lock (<reason>); nothing was sent to <address>, and the history now reads it as uncertain`. The other run reads that recipient as uncertain and does not send it by itself. The history shows it with the message `the run ended before the outcome of this send was recorded (crash, kill or power loss)`, although the provider was not called.
- **Snapshot, journal and upgrade.** Before, a run that lost its lock could still finish writing its snapshot and delete the journal, cut off a torn last journal line, or upgrade a v1 history, erasing the records of the run that took the list over, which a later run then sent again. The run now checks the lock right before each step that replaces, shortens or deletes a history file, and stops without it. The causes read `the send state of "<template>" · <file.csv> can only be written by the store that holds its lock, and while preparing the history files this run could no longer confirm that it holds it (<reason>); it stopped before changing them further`, and, when the snapshot was already written, `the snapshot of the send state of "<template>" · <file.csv> was written, but right after it this run could no longer confirm that it holds its lock (<reason>); the journal was kept, so no record written by another run was removed`.

Limits: this is not exactly-once delivery.

- Each check and the step it protects are separate file-system calls. A run suspended by the operating system between the two, for as long as another run takes the list, sends and writes its history, can still overwrite that history, which erases every send the other run recorded, so a later `pending` run sends them all again. The same goes for a journal line it was already appending. For example, a late `failed` outcome written after the other run was deliberately told to resend that recipient (`subset` or `force-all`) and recorded `sent` is read last, and a `failed-only` run then sends the message again, unless the other run wrote its snapshot after that line.
- The checks treat the lock as the run's own only while the lock file holds its token and is the same file (device and file number). A deleted lock that comes back, restored by hand or by a sync tool, fails the check unless the file system gives the copy the file number of the deleted file, which file systems can do.
- When the lock file cannot be read (for example `EMFILE`, `EIO` or `ESTALE`), the run stops as if it had lost the lock, and says that nothing was sent to the recipient; the lock may in fact still be its own.
- The checks rely on every run seeing, at once, the files another process has just written. That holds on local disks and is likely on NFS. It is not established on SMB shares, Windows folders opened from WSL, or folders synced by iCloud, OneDrive, Dropbox or Syncthing.
- A run of an earlier mailroll that shares the folder makes none of these checks, so mixing versions on one list keeps the old risk.
- A program that runs `runTemplate` with its own state store that takes no lock gets none of this protection.
- A send that times out at the provider stays uncertain.
