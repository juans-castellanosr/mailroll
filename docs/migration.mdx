mailroll 0.2 changes three things:

- **Packages.** Outlook moved out of mailroll into `@mailroll/outlook`. This page starts with that.
- **Send history.** It moves to a new format the first time a live run writes to each list, and mailroll 0.1 can no longer read it after that. See [Send history v2](#send-history-v2).
- **SDK types and JSON output.** Some types gained required fields, and the run summary and `status` gained new fields. See [History v2 and SDK types](#history-v2-and-sdk-types).

mailroll is now split into three packages, and none of them makes a provider mandatory:

| Package | What it is |
| --- | --- |
| `@mailroll/core` | The provider-independent engine and integration contracts. No dependencies; it runs in Node.js and browsers. |
| `mailroll` | The CLI and the Node.js SDK. It depends on `@mailroll/core` and includes no integration. |
| `@mailroll/outlook` | The official Microsoft Outlook (Microsoft Graph) integration, and the `mailroll-outlook` tool. |

If you sent through Outlook, install the integration and declare it, exactly like any other [integration](/guides/integrations):

```bash Terminal
npm install @mailroll/outlook
```

```json mailroll.json
{ "integrations": ["@mailroll/outlook"] }
```

Without the declaration, every run refuses Outlook connections, dry runs included: `connection "outlook-1" uses the integration "outlook", which is not active`.

## What stays the same

- **Connections** keep `"kind": "outlook"`. Campaign, template and connection files do not change.
- **Secrets** keep their names: `<CAMPAIGN>__<CONNECTION>__TENANT_ID` and `<CAMPAIGN>__<CONNECTION>__CLIENT_ID`. See [Connection secrets](/reference/environment#connection-secrets).
- **The token cache** stays where it was, `<TOKEN_CACHE_PATH>/<campaign>/<connection>.json`, and is reused as it is: no new sign-in, nothing to migrate or delete. See [Token cache](/reference/files#token-cache).
- **The send history** stays in the same files, and every recorded status keeps its meaning. Its format changes on the first live run; see [Send history v2](#send-history-v2).

## Commands

| Before | Now |
| --- | --- |
| `mailroll export-sent …` | `mailroll-outlook export-sent …` (from `@mailroll/outlook`), with the same options, output file and exit codes. See [mailroll-outlook export-sent](/outlook/export-sent). |

`mailroll-outlook` reads your campaigns through mailroll, so install both in the same project.

## Imports

The Outlook exports moved from `mailroll` to `@mailroll/outlook`:

| Before, from `mailroll` | Now, from `@mailroll/outlook` |
| --- | --- |
| `outlookIntegration` | the default export, or `outlookIntegration` |
| `createOutlookIntegration`, `OutlookIntegrationOptions`, `OutlookSettings` | the same names |
| `GraphClient`, `GraphClientOptions`, `FetchFn` | the same names |
| `OutlookAuthProvider`, `OutlookAuthOptions`, `OutlookConfigResolver`, `OutlookConnectionConfig`, `SignInMode` | the same names |
| `OutlookProviderFactory` | the same name |
| `SentItemsReader`, `SentItemsReaderOptions`, `SentMessage` | the same names |

`@mailroll/outlook` also exports `OUTLOOK_INTEGRATION_ID`, `outlookTokenCachePath` and `GraphSendOptions`. The library needs only `@mailroll/core`, so you can use it without mailroll.

## SDK runs

`runSelection` no longer activates Outlook by default: when `integrations` is omitted, no integration is active. Pass the integrations your connections use:

```ts
import { ConsoleLogger, runSelection } from 'mailroll';
import outlook from '@mailroll/outlook';

await runSelection(
  {
    campaignId: 'acme/onboarding',
    targets: [{ templateId: 'welcome' }],
    connectionIds: ['outlook-1'],
    policy: { kind: 'pending' },
    mode: { kind: 'dry-run' },
  },
  { campaignsRoot: 'campaigns', logger: new ConsoleLogger(), integrations: [outlook] },
);
```

`mailroll` also gained `connectionStateLocation`, which returns the state folder and key that a connection's integration receives, for tools that work with that state outside a run.

## Send history v2

The first live run of mailroll 0.2 that writes to a list upgrades its history from the v1 format of mailroll 0.1 to v2:

- The old snapshot is copied to `<stem>.json.v1-backup` and the old journal is moved, unchanged, to `<stem>.jsonl.v1-backup`. Neither is ever overwritten.
- Every recorded status keeps its meaning. The upgrade adds no evidence the old files did not have.
- **It is one-way.** After it, mailroll 0.1 refuses the list with `invalid state file`, so it can never write over v2 history. Going back is only safe while nothing has been sent with 0.2; see [Restoring the v1 files](/reference/files#restoring-the-v1-files).
- Dry runs, test sends, `status` and the menu read v1 histories without upgrading them. Dry runs, test sends and `status` say that the next live run will upgrade the list.
- If the upgrade is interrupted, the next live run finishes it.

Details are in [Upgrade from the v1 format](/reference/files#upgrade-from-the-v1-format). Read [Platforms and limits](/reference/files#platforms-and-limits) before you upgrade: the new format needs a file system with hard links, and Windows and macOS have not been verified yet.

## Behavior that changed

- A run **needs attention**, and the CLI exits with `1`, when the provider rejected the CC of a message whose template requires one. A rejected optional CC does not change the exit code. The main recipient is `sent` in both cases and is not sent again. See [Rejected CC](/guides/history#rejected-cc).
- The JSON of `send --json` gained `counts.ccRejectedMessages`, `counts.requiredCcRejectedMessages`, `ccRejected` and `history`, and `attention` entries can have the status `cc-rejected`, which names a recipient whose message **was accepted**. A script that treats every attention entry as "not delivered" must handle it. See [Automation](/guides/automation).
- The JSON of `status --json` gained the two CC counts, `history` and `evidence`.
- The history records evidence for tracing: `attemptId`, `providerMessageId`, `cc` and `uncertainAttemptIds`. It never proves delivery.
- A snapshot's `updatedAt` is now the `at` of the last recipient entry recorded, not the time the snapshot was written. An entry that kept an earlier status and only added a `resendFailure` keeps that earlier `at`.
- An intent followed by another intent for the same recipient, with the later one released, now reads as uncertain instead of disappearing. This prevents a resend whose outcome was never known.
- `FileStateStore` refuses every write unless the same instance holds the list's lock and loaded the list after taking it, and it stops writing if the lock file is deleted or taken over during the run. Code that called `append` or `compact` without `lock()` now gets `ConfigError`. Inside `runTemplate` or `runSelection`, the refusal arrives as the `cause` of a `StatePersistenceError` (`could not record send state …`), not as a `ConfigError`; see [History stores](/sdk/nodejs#history-stores). `runTemplate` also refuses a second concurrent live run of the same list on the same store, `MemoryStateStore` included.
- The lock file holds a `token`, and a stale lock is recovered under a `<stem>.json.lock.recover` file. A run that ends during a recovery can leave that file behind, and the next live run then stops until you delete it. See [Locks](/guides/history#locks).
- Locks are created with hard links, so on a file system without them every live run stops before sending, not only runs that write a new journal.

## History v2 and SDK types

Code that only reads results and calls `needsAttention` keeps compiling. Code that builds these values, or implements a `StateStore`, does not:

| Change | Runtime | Types | Saved history |
| --- | --- | --- | --- |
| `TemplateState` is `version: 2`; `StateStore.load` returns `StoredTemplateState` | Your store may keep returning v1 data | **Breaks** stores that return `version: 1` as `TemplateState`, and code that assigns `load()` to `TemplateState` | Unchanged for your store; `FileStateStore` writes v2 |
| `compact` receives a v2 state | A store that checks `version === 1` there never sees it | **Breaks** the comparison | Your store saves v2 from now on |
| `RunReport` gained `ccRejectedMessages`, `requiredCcRejectedMessages` | Always present | **Breaks** hand-built reports | — |
| `TemplateRunResult` gained `history` | Always present | **Breaks** hand-built results | — |
| `ListCounts` gained the two CC counts; `ListReport` gained `evidence` (and `history` when known) | Always present | **Breaks** hand-built counts and reports | — |
| `emptyState()` returns `version: 2` | Changes stored data of stores that save it | Compiles | — |
| New optional fields on `RecipientStatus`, `ResendFailure`, `RecipientJournalEntry` and `SendResult` | — | Compile | Written by `FileStateStore` |

New exports: `CcObservation`, `StoredTemplateState`, `TemplateStateV1`, `foldJournal` and `upgradeTemplateState` in `@mailroll/core` (and `mailroll`), and the types `RunHistory` and `HistoryPresence` in `mailroll`. Nothing was removed.

A store that implements `StateStore`. `load` may keep returning what you saved before 0.2, and `compact` saves v2:

```ts
import {
  emptyState,
  type RecipientJournalEntry,
  type ResolvedTemplate,
  type StateLock,
  type StateStore,
  type StoredTemplateState,
  type TemplateState,
} from 'mailroll';

const saved = new Map<string, StoredTemplateState>();

export const store: StateStore = {
  load: (template: ResolvedTemplate): Promise<StoredTemplateState> =>
    Promise.resolve(saved.get(template.statePath) ?? emptyState(template.id)),
  append: (_template: ResolvedTemplate, _entry: RecipientJournalEntry): Promise<void> => Promise.resolve(),
  compact: (template: ResolvedTemplate, state: TemplateState): Promise<void> => {
    saved.set(template.statePath, state);

    return Promise.resolve();
  },
  lock: (): Promise<StateLock> => Promise.resolve({ release: () => Promise.resolve() }),
};
```

Reading a store's history as a `TemplateState`:

```ts
import { type ResolvedTemplate, type StateStore, type TemplateState, upgradeTemplateState } from 'mailroll';

export async function currentState(store: StateStore, template: ResolvedTemplate): Promise<TemplateState> {
  return upgradeTemplateState(await store.load(template));
}
```

Telling data saved before 0.2 apart, on what `load` returned rather than inside `compact`:

```ts
import type { StoredTemplateState } from 'mailroll';

export const savedBefore02 = (stored: StoredTemplateState): boolean => stored.version === 1;
```

Building a `RunReport`, for example in a test. `report()` computes every count:

```ts
import { report, type RunReport } from 'mailroll';

export const empty: RunReport = report([]);
export const handmade: RunReport = {
  total: 0,
  sent: 0,
  failed: 0,
  uncertain: 0,
  notAttempted: 0,
  skipped: 0,
  heldUncertain: 0,
  ccRejectedMessages: 0,
  requiredCcRejectedMessages: 0,
  results: [],
};
```

Building a `TemplateRunResult`:

```ts
import { report, type RunHistory, type TemplateRunResult } from 'mailroll';

const history: RunHistory = { before: 'v2', upgraded: false };

export const result: TemplateRunResult = {
  templateId: 'welcome',
  dataFile: 'recipients.csv',
  policy: 'pending',
  statePath: 'campaigns/acme/onboarding/templates/welcome/.state/recipients.json',
  report: report([]),
  history,
};
```

Building `ListCounts` and a `ListReport`:

```ts
import type { ListCounts, ListReport } from 'mailroll';

const counts: ListCounts = {
  total: 1,
  sent: 1,
  failed: 0,
  uncertain: 0,
  pending: 0,
  rejected: 0,
  ccRejectedMessages: 0,
  requiredCcRejectedMessages: 0,
};

export const list: ListReport = { dataFile: 'recipients.csv', counts, evidence: [] };
```
