mailroll keeps everything on disk: your campaign files, the send history of each list, preview files, saved sign-ins and Sent Items exports. This page describes each of them. Read [State files](#state-files) before you move, edit or delete anything in a `.state/` folder.

## Overview

All relative paths below are resolved against the current working directory, except the paths inside a campaign, which are relative to the campaign folder.

| Path | mailroll | Section |
| --- | --- | --- |
| `<campaign>/…` configuration and code | Reads | [Campaign files](#campaign-files) |
| `templates/<id>/data/*.csv` | Reads | [CSV lists](#csv-lists) |
| `templates/<id>/view/compiled.html` | Writes (`build-template`) | [Campaign files](#campaign-files) |
| `templates/<id>/.state/` | Reads; writes in live sends | [State files](#state-files) |
| `previews/` | Writes in dry runs | [Previews](#previews) |
| `.secrets/tokens/` | Reads and writes | [Token cache](#token-cache) |
| `mailroll-outlook export-sent` output file | Writes | [Sent Items export](#sent-items-export) |
| `.env` | Reads (CLI only) | [Environment variables](/reference/environment) |
| `mailroll.json` | Reads (CLI only) | [Integrations](#integrations) |
| `node_modules/.cache/mailroll/import.mjs` | Writes once, then reads (CLI only) | [Integrations](#integrations) |

mailroll writes no log files. Logs and progress go to stderr.

## Campaign files

These files are yours: mailroll reads them whenever it loads your campaigns, and changes only `compiled.html`, and only when you run `build-template`.

- `campaign.config.json`, `connections/*.json` and `config/template.config.json` are described field by field in [Configuration files](/reference/configuration).
- `code/plugin.ts` is your template plugin. mailroll looks for `plugin.ts`, `plugin.mts`, `plugin.js` and `plugin.mjs`, in that order, and uses the first it finds. It **imports and runs this file** with your user's permissions, also during `mailroll status` and in the menu, so treat it like any other code you execute. Its default export must be a `definePlugin(...)` result. See [Templates](/guides/templates).
- `view/compiled.html` is the email HTML. mailroll does not read it by itself; your plugin loads it, usually with `loadCompiledTemplate`. You can write it by hand, or generate it from `view/template.mjml` with [`mailroll build-template`](/cli/build-template), which overwrites it every time.
- `view/template.mjml` is read only by `build-template`.

## CSV lists

Each `.csv` file in `templates/<id>/data/` is one recipient list. The extension is matched case-insensitively. The full rules (UTF-8, header row, the `email` column, duplicates) are in [Create a campaign](/guides/campaigns).

mailroll never writes to a CSV. It does compute a SHA-256 fingerprint of the file while it prepares a run and checks it again before sending each list. If the file changed in between, the run stops with `… changed after the run was prepared; nothing more was sent — run again`.

The CSV's name decides its state file name, so renaming a CSV starts a new, empty history for it. See [State files](#state-files).

## State files

Every list (one template and one CSV) has its own send history in the template's `.state/` folder. It is what lets mailroll skip recipients who already received a message and hold back the ones whose outcome is uncertain. What it means for your sends is explained in [History](/guides/history); this section describes the files.

### Names

The file names share a stem made from the CSV's name without `.csv`: every run of characters other than ASCII letters and digits becomes `_`, and leading and trailing `_` are removed. Letter case is kept.

| CSV | Snapshot | Journal | Lock |
| --- | --- | --- | --- |
| `recipients.csv` | `recipients.json` | `recipients.jsonl` | `recipients.json.lock` |
| `VIP list.csv` | `VIP_list.json` | `VIP_list.jsonl` | `VIP_list.json.lock` |

A CSV whose name has no letter or digit is rejected, and so are two CSVs that produce the same stem (`VIP list.csv` and `VIP-list.csv`), because their histories would mix.

A list upgraded from the history format of mailroll 0.1 also keeps `<stem>.json.v1-backup` and `<stem>.jsonl.v1-backup`; see [Upgrade from the v1 format](#upgrade-from-the-v1-format). No CSV can produce those names.

### Who writes them

Only live sends write state. Dry runs, test sends, `mailroll status` and the menu read it, to apply the resend policy and show it, but never change it, and never upgrade a v1 history. mailroll creates the `.state/` folder the first time it needs it. Each file is created with permissions `0600` (read and write for your user only). The journal backup `<stem>.jsonl.v1-backup` is the v1 journal itself, moved, so it keeps the permissions that file had.

### Format versions

This page describes the **v2** history format of mailroll 0.2. mailroll 0.2 still reads the **v1** format of mailroll 0.1, and upgrades a list to v2 the first time a live run writes to it. The upgrade is one-way: mailroll 0.1 refuses a v2 history.

### Snapshot

`<stem>.json` holds the last known status of every recipient that was ever sent to from this list. It is a JSON object, written with two-space indentation. This illustrative snapshot shows the three possible statuses and the optional evidence fields:

```json templates/welcome/.state/recipients.json wrap
{
  "version": 2,
  "templateId": "welcome",
  "recipients": {
    "ana@example.com": {
      "status": "sent",
      "at": "2026-01-15T10:00:01.120Z",
      "connectionId": "relay-1",
      "attemptId": "6f1c2a9e-3b4d-4c8e-9a10-2b7d5e8f1a33",
      "providerMessageId": "<20260115100001.4821@mail.example.com>",
      "cc": { "rejected": ["records@example.com"], "required": true }
    },
    "ben@example.com": {
      "status": "failed",
      "at": "2026-01-15T10:00:01.480Z",
      "connectionId": "outlook-1",
      "category": "permanent",
      "message": "Microsoft Graph sendMail failed (HTTP 400): {\"error\":{\"code\":\"ExampleError\"}}",
      "attemptId": "0d9e8c7b-6a5f-4e3d-8c2b-1a0f9e8d7c6b"
    },
    "cleo@example.com": {
      "status": "uncertain",
      "at": "2026-01-15T10:02:03.900Z",
      "connectionId": "outlook-1",
      "message": "no answer from Microsoft Graph within 120 s; the message may or may not have been sent",
      "attemptId": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d",
      "uncertainAttemptIds": ["9f8e7d6c-5b4a-4c3d-9e2f-1a0b9c8d7e6f"]
    }
  },
  "updatedAt": "2026-01-15T10:02:03.900Z"
}
```

- `recipients` is keyed by the address in lower case. Recipients who were never sent to, and rows the template rejected, do not appear.
- `status` is `sent`, `failed` or `uncertain`. Every status has `at` (ISO 8601 time) and `connectionId`.
  - `sent` means the provider **accepted** the message. It never means the message was delivered or read.
  - `uncertain` means mailroll cannot tell whether the provider accepted it. mailroll never resends it on its own.
- `category`, on failed entries only, is `transient`, `permanent` or `throttled`. Authentication failures are never recorded: the intent is released and the recipient keeps its previous status. The file format also accepts `auth`, but mailroll does not write it.
- `message`, on failed and uncertain entries, is the error text.
- `resendFailure` may appear on `sent` and `uncertain` entries. It records a later attempt that failed or became uncertain without replacing the earlier status, with the fields `at`, `connectionId`, `outcome` (`failed` or `uncertain`), `message`, `attemptId` when known and, for failures, `category`.
- `updatedAt` is the `at` of the last recipient entry the run recorded. When that entry kept an earlier `sent` or `uncertain` status and only added a `resendFailure`, its `at` is the earlier time, so `updatedAt` can be older than the run. A live run that records no outcome keeps the previous value, which for a new list is `1970-01-01T00:00:00.000Z`.

The evidence fields are optional. They are written only when mailroll actually has the information, and they help you trace a message with your provider. None of them proves delivery.

- `attemptId` identifies the send intent that produced the entry: one intent per recipient and run, kept the same across the retries of that intent. Entries written by mailroll 0.1, and sends through email providers that do not receive attempt ids, have none.
- `providerMessageId`, on sent entries, is the identifier the integration returned for the accepted message, unchanged. Integrations that return none (the Outlook integration among them) leave it out.
- `cc`, on sent entries, appears only when the integration reports each recipient separately and the message had a CC. `rejected` lists the CC addresses the provider refused, and `required` says whether the template's `ccPolicy` was `required` **when the message was sent**, so changing the template later does not change it. A missing `cc` means the CC was not observed, never that every CC was accepted.
- `uncertainAttemptIds` lists the attempt ids of earlier intents for this recipient that ended uncertain and are no longer shown elsewhere in the entry, in the order they happened. They stay even when a later deliberate resend succeeds, because each of them may have been delivered.

A v2 snapshot with a field mailroll does not know is refused (`invalid state file at <path>: …`), so nothing is silently dropped.

### Journal

`<stem>.jsonl` records each send as it happens, one JSON object per line. Its first line is the format header. Before each message is sent, mailroll appends an intent; after it, the outcome. Each line is flushed to disk before mailroll continues. These illustrative lines show the header and the three entry kinds:

```json templates/welcome/.state/recipients.jsonl wrap
{"format":"mailroll-journal","version":2}
{"email":"ana@example.com","intent":{"at":"2026-01-15T10:00:00.870Z","connectionId":"outlook-1","attemptId":"6f1c2a9e-3b4d-4c8e-9a10-2b7d5e8f1a33"}}
{"email":"ana@example.com","status":{"status":"sent","at":"2026-01-15T10:00:01.120Z","connectionId":"outlook-1","attemptId":"6f1c2a9e-3b4d-4c8e-9a10-2b7d5e8f1a33"}}
{"email":"dan@example.com","intent":{"at":"2026-01-15T10:00:01.400Z","connectionId":"outlook-2","attemptId":"0d9e8c7b-6a5f-4e3d-8c2b-1a0f9e8d7c6b"}}
{"email":"dan@example.com","released":{"at":"2026-01-15T10:00:01.700Z"}}
```

- An `intent` line means a send is about to start, with the `attemptId` of that intent when there is one.
- A `status` line is the outcome, in the same shape as a snapshot entry.
- A `released` line withdraws an intent for a message the provider did not accept: its connection was stopped (authentication failed, the provider refused the whole connection, or its retries ran out), or the run was stopped before the message was sent or while it waited for a retry.

When mailroll loads a list, it reads the snapshot and replays the journal over it:

- An intent with neither an outcome nor a release means the process ended mid-send, so that send is **uncertain**, with the message `the run ended before the outcome of this send was recorded (crash, kill or power loss)` and the intent's `attemptId`. It is combined with the recipient's previous status like any other outcome: a recipient that was not sent becomes `uncertain`, and a recipient that was already `sent` stays `sent` with the uncertain attempt in `resendFailure`.
- An intent followed by another intent for the same recipient, with nothing in between, also ended without an outcome. It is read as uncertain in the same way, even when the later intent was released, so it is never sent again on its own.

### Lock

`<stem>.json.lock` marks a list as being sent. It contains the owner of the run, a `token`, a random id that only that run knows, and `pidSpace`, the process space the run belongs to:

```json templates/welcome/.state/recipients.json.lock wrap
{"pid":48213,"host":"build-01","startedAt":"2026-01-15T09:59:58.300Z","token":"0b8f1c52-6a3e-4f7d-9c21-5e4a7d3b9f60","pidSpace":"linux:11111111-2222-4333-8444-555555555555:4:4026531836"}
```

A run releases a lock, and writes the list's history, only while the lock file is still the file that run created (the same file on disk, not a copy with the same content) and holds its own `token`. It checks the lock again after writing each send intent and right before each step that replaces, shortens or deletes a history file, and stops without that step if the lock is no longer its own. A copy of the lock put back by a sync tool such as OneDrive, Dropbox or Syncthing, or by a restored backup, is not taken for the run's own lock, unless the file system happens to give the copy the inode number the original had, which some file systems reuse once a file is deleted. To release its lock, a run moves it aside to `<stem>.json.lock.stale-<id>`, checks that the moved file is its own, and removes it. If it is not, because the lock was deleted by hand and another run created its own in the meantime, mailroll never puts it back, because by then a third run may have taken and used the list: it keeps the moved file as `<stem>.json.lock.stale-<id>`, leaves the lock path as it is, and stops with `<path> was replaced while this run was releasing its own lock, which only happens if someone deleted it by hand; nothing was deleted: the replacement is kept as <stem>.json.lock.stale-<id>, and the run whose lock it is will stop at its next check. …`. The run whose lock was moved no longer finds it and stops at its next check.

The process space says where the process id `pid` is meaningful. On Linux it is the kernel's boot id (`/proc/sys/kernel/random/boot_id`) and the identity of the run's PID namespace (`/proc/self/ns/pid`): two containers, or a container and its host, have different PID namespaces even when they have the same host name, and a restart changes the boot id. If only one of the two can be read, the process space is left out. On macOS and Windows it is the platform and the host name, which tells apart nothing more than the host name already does. On any other platform it is always left out.

A second live run of the same list fails before sending with `the send state of "…" · … is in use by another run (process P on H, since T). Wait for it to finish; if no run and no lock recovery is active on this list (<path>.recover does not exist), delete <path>`. mailroll recovers a lock automatically, with a `state.lock_recovered` warning in the logs, only when it can prove that its owner is gone: same host name, same process space, and no process with that id. Otherwise it keeps the lock and stops before sending with `… is in use by another run (process P on H, since T), and mailroll cannot tell whether that process is still running: <reason>`. The reason names the boot ids and PID namespaces that differ, and the message tells you what to check before deleting the lock by hand. mailroll prefers this stop to a guess, because a wrong guess lets two runs send to the same list. So a stale lock is never recovered automatically, and needs you to delete it, when it was left:

- before the machine restarted;
- by a container that has been restarted or removed since, or by another container or the host outside it;
- on another machine with the same host name;
- by mailroll 0.1, or by any lock without `pidSpace`;
- on a platform other than Linux, macOS or Windows, or by a run that could not read its own process space.

See [Locks](/guides/history#locks).

mailroll creates a lock by writing it to a temporary file and hard-linking it into place, so a lock is never half written and never replaces another one. Recovery works under a second file, `<stem>.json.lock.recover`, which holds the owner of the recovery in the same format. While it exists, other runs do not touch the lock. If its owner is in another process space, mailroll cannot tell a recovery in progress from an interrupted one and stops with `… cannot be recovered: <path>.recover shows that process P on H, since T, is recovering <path> or stopped while doing so, and mailroll cannot tell whether that process is still running: <reason>`. The recovering run moves the stale lock aside to `<stem>.json.lock.stale-<id>`, removes it, and creates its own lock. If the moved file is not the stale lock it checked, because the lock was replaced by hand in the meantime, it is never removed: the moved file must be the same file on disk and hold the same owner, so a replacement that the file system gave the inode number of the deleted lock is caught too. It is never put back either: it stays as `<stem>.json.lock.stale-<id>`, and the recovery stops with `the lock <path> was replaced while it was being recovered, which only happens if someone deleted it by hand during the recovery; nothing was deleted: the replacement is kept as <stem>.json.lock.stale-<id>, and the run whose lock it is will stop at its next check. …`.

<Note>
  The CLI and `runSelection` always take the lock before writing. A program that calls `FileStateStore` directly must do the same, with one instance: call `lock()`, then run the list (`runTemplate` loads it again after the lock is taken), then call `release()` on the lock in a `finally` block. Any other write is refused with `ConfigError` and writes nothing: the instance does not hold the lock, it did not load the list after taking it, or its lock file no longer holds its `token` or cannot be read.
</Note>

### Lifecycle

A live run touches the state files in this order:

1. While the run is prepared, mailroll loads the state of every selected list, then takes the lock of every list before the first message is sent.
2. The first write to a list prepares its files: it upgrades a v1 history (see below) or, for a new list, writes an empty v2 snapshot first, and then starts the journal with its header.
3. For each message, it appends an intent line, sends, and appends the outcome line.
4. When a list finishes or stops, mailroll writes a new snapshot to a temporary file, renames it over `<stem>.json`, and deletes the journal. If any intent is still open, for example after a history write failed, it keeps the journal instead and logs `state.journal_kept` with the reason `an intent is still open`, so the open intent is not lost. If the snapshot itself cannot be written after the list already stopped on an error, it logs `state.flush_failed` and reports the first error; otherwise the run fails with `could not record send state snapshot; …`. Either way the journal stays, and the next run replays it.
5. When the run ends, successfully or not, it deletes its locks. A failure to delete one is logged as `state.lock_release_failed` and does not change the run's result.

Every history file mailroll writes is flushed to disk, and so is the folder after a history file is created, renamed or removed. The lock file's content is flushed, and so is its folder when the lock is created; the folder is not flushed when the lock is deleted. On Windows the folder flush is skipped when Windows refuses it; see [Platforms and limits](#platforms-and-limits).

### Upgrade from the v1 format

A list written by mailroll 0.1 is upgraded at the first write of a live run of mailroll 0.2, while that run holds the list's lock:

1. mailroll checks that the v1 snapshot and journal hold only v1 data. If not, it stops without changing anything.
2. It copies the v1 snapshot, byte for byte, to `<stem>.json.v1-backup`.
3. It writes a v2 snapshot that contains the v1 snapshot with the v1 journal replayed over it. From this point on, mailroll 0.1 refuses the history with `invalid state file`, so it can never write over v2 data.
4. It moves the v1 journal, unchanged, to `<stem>.jsonl.v1-backup`. An empty v1 journal is deleted instead.
5. It starts the v2 journal with its header.

The upgrade adds no evidence the v1 files did not have: v1 entries keep no `attemptId`, `providerMessageId`, `cc` or `uncertainAttemptIds`.

A backup is never overwritten. If one already exists with the same content, from an upgrade that was interrupted, it is reused. If it exists with other content, the run stops with `… already exists with other content …`. Because the upgrade happens at the first write, this refusal and the one in step 1 reach you inside a history-write error, not on their own; see [Damaged or incompatible state](#damaged-or-incompatible-state).

If the process stops in the middle of the upgrade, the files remain readable with the same history, and the next live run finishes the upgrade. The tests check this by making each write, rename, removal and flush fail in turn, inside the process, for an upgrade started by a send. An upgrade started by a live run with nothing to send, which only writes the snapshot, is not part of those checks.

The live run's summary reports `history upgraded to v2` only after it has found the v2 snapshot and the backups on disk. In JSON, the list's `history` is `{"before": "v1", "upgraded": true, "backups": [...]}`, and the log has a `state.history_upgraded` event. A dry run or test send of a v1 list says `history is in the v1 format; the next live run upgrades it to v2 (one-way)`.

### Restoring the v1 files

Only restore the v1 files if you must go back to mailroll 0.1, **and only if mailroll 0.2 never attempted a send to that list**. Restoring forgets everything 0.2 recorded, so a message it sent, or one whose outcome is uncertain, would be sent again by the next `pending` run of mailroll 0.1.

The files cannot prove this on their own. A list that finished has no journal, because mailroll deletes it when it writes the snapshot, and a resend changes a recipient's status without adding a recipient. Restore only if both of these are true:

- `<stem>.jsonl` is absent or holds only its header line.
- You have the summary of every live run of mailroll 0.2 on that list, the one that upgraded it included, and each one reports `sent 0, failed 0, uncertain 0` for the list. No run on the list was interrupted before it printed its summary.

If you cannot confirm both, do not restore.

With no run active on the list:

1. Rename `<stem>.json` to a name of your choice, for example `<stem>.json.v2-abandoned`. Keep it.
2. If `<stem>.jsonl` holds only its header line, remove it.
3. Rename `<stem>.json.v1-backup` to `<stem>.json` if it exists, and `<stem>.jsonl.v1-backup` to `<stem>.jsonl` if it exists. A list that had only a v1 journal has no snapshot backup.

mailroll never does this by itself.

### Damaged or incompatible state

| Problem | What mailroll does |
| --- | --- |
| Last journal line cut off by a crash | Ignores it; removes it before the next append |
| Last journal line complete but without its newline | Reads it; adds the newline before the next append |
| Any other journal line unreadable | Stops: `corrupt state journal at <path> (line N)` |
| Last line of a v2 journal complete but unreadable | Stops: `corrupt state journal at <path> (line N)`, and never writes after it |
| Snapshot is not valid JSON | Stops: `corrupt state file at <path>` |
| Snapshot has the wrong shape, or a v2 snapshot has an unknown field | Stops: `invalid state file at <path>: …` |
| Snapshot or journal from a newer mailroll | Stops: `… written by a newer mailroll; upgrade mailroll to use this history` |
| v2 journal next to a v1 snapshot, or with no snapshot | Stops: `… mixes a v2 journal with … snapshot …` |
| v1 file with data mailroll cannot keep, at upgrade | Stops at the first write without changing anything: `cannot upgrade the state file at <path>: …` or `cannot upgrade the state journal at <path>: line N …`; the list can still be read |
| Backup exists with other content, at upgrade | Stops at the first write without changing anything: `cannot upgrade the send history: <path>.v1-backup already exists with other content …` |
| Journal disappeared during a live run | Stops at the next history line: `the state journal at <path> disappeared during the run; nothing was written, and the run stops so no send goes unrecorded` |
| Journal created by something else during a live run, before the run's first line | Stops at that line: `the state journal at <path> appeared before this run wrote to it, so something else created it: another program while this run held the list's lock, or another run that took the lock after this run lost it; nothing was written` |

The `corrupt`, `invalid`, newer-mailroll and mixed-format stops are found when the list is read. A run reads every list before it signs in or sends, and `runTemplate` reads its list before it starts, so these messages arrive on their own, as `ConfigError`. The last four rows happen when the run writes. A direct `append` or `compact` call on a `FileStateStore` throws them as `ConfigError`. During a run, from the CLI, `runSelection` or `runTemplate`, they arrive as the cause of a `StatePersistenceError`, after the stage of the write that was refused: for example `could not record send state before sending to <address>; …: ConfigError: cannot upgrade the state file at <path>: …`, or `could not record send state snapshot; …: ConfigError: …` for a list with nothing left to send. One of the read stops arrives in this form too if the file changed after the list was read and before the run's first write to it. See [Could not record send state](/troubleshooting#could-not-record-send-state).

A cut-off last line is what a crash during a write leaves behind, so it is safe to drop. Anything else needs you to restore the file from a backup or fix it by hand. Until then, sends of that list stop on it, and `mailroll status` reports it as a problem of the template.

### What is safe to delete

| File | Safe to delete | What you lose |
| --- | --- | --- |
| `<stem>.json.lock` | Only when no run and no lock recovery uses the list, on any machine, and `<stem>.json.lock.recover` does not exist | Nothing |
| `<stem>.json.lock.recover` | Only when no run and no lock recovery uses the list, on any machine; delete it before the lock | Nothing |
| `<stem>.json.lock.stale-<id>` | When no lock recovery is active | Nothing; a lock that was being recovered or released, or the lock of a run that has already lost it and stops at its next check |
| `<stem>.jsonl` | No | Outcomes since the last snapshot |
| `<stem>.json` | Only to forget the list's history | Every recorded status |
| `<stem>.json.v1-backup`, `<stem>.jsonl.v1-backup` | When you will never need to go back to mailroll 0.1 | The way back to 0.1; the current history is not affected |
| `*.tmp` next to them | When no run is active | Nothing; never read |

A crash or kill can leave files behind:

- A `.tmp` file, if the process ended while writing one of these files. Its name is the name of the file being written, followed by a random id: `<stem>.json.<id>.tmp` for a snapshot, `<stem>.jsonl.<id>.tmp` for a new journal, `<stem>.json.v1-backup.<id>.tmp` for the backup of a v1 snapshot, `<stem>.json.lock.<id>.tmp` for a lock, and `<stem>.json.lock.recover.<id>.tmp` for a recovery marker. mailroll never reads it.
- `<stem>.json.lock.stale-<id>`, if the process ended in the middle of a recovery or of a release, if the moved lock could not be removed, or if the moved lock turned out to belong to another run; the error then names it. mailroll never reads it.
- `<stem>.json.lock.recover`, from the same cause. The next live run stops with `… cannot be recovered: an earlier recovery of <path> did not finish and left <path>.recover (…)`, which tells you to check that no run and no recovery is active and then delete the marker. See [Locks](/guides/history#locks).

<Warning>
  Deleting or editing a snapshot or journal can cause duplicate emails. A recipient missing from the history counts as never sent to, so the next live run with the `pending` policy sends to them again, including recipients whose earlier send was uncertain. If you want a fresh history for a new mailing, give the CSV a new name instead: it gets its own state files and the old history stays intact.
</Warning>

Delete a lock by hand only after making sure the run that owns it has ended, for example a run on another machine or in another container that shares the folder. mailroll cannot check processes on other hosts or in other process spaces, so it never recovers those locks itself.

### Platforms and limits

These limits are known and not yet solved:

- **Hard links are required.** Locks, backups and new journals are created with hard links, so they never overwrite an existing file, and there is no fallback without them. On file systems without hard links, such as FAT or exFAT drives and some network or synchronized folders, every live run stops before sending anything when it takes the first lock, with `could not create …/.state/<stem>.json.lock; nothing was left behind`. The reason from the file system is in the error's `cause`. Dry runs, test sends and `status` are not affected.
- **Windows and macOS are not verified yet.** The test suite includes real file-system checks for both, but they have not run there. Windows does not let Node.js flush a folder to disk, so on Windows mailroll skips that step when the flush is refused with `EPERM`; any other error still stops the write. The creation, renaming or removal of a state file is then not flushed explicitly: a journaling file system such as NTFS keeps the folder consistent after a crash, but the latest such change may be lost on power failure, and on a network share it depends on the server.
- **Durability depends on the file system and the operating system.** mailroll flushes files, and folders everywhere except Windows. On macOS, Node.js asks for a full flush (`F_FULLFSYNC`), which also empties the disk's own write cache; where the file system does not support it, as on some network or mounted volumes, Node.js falls back to a weaker flush that only orders writes, and mailroll cannot tell which one took place. Power loss is not simulated in the tests, and the process is not killed: the tests make each file operation fail in turn instead.
- **Process spaces.** Automatic lock recovery trusts the process space to tell apart processes that share a host name.
  - On Linux, two PID namespaces that exist at the same time never share an identity, and the boot id changes at every restart, so containers on one machine, and one machine before and after a restart, are told apart. This was verified with Podman on one Linux kernel.
  - Sandboxes that run their own kernel in user space and report their own `/proc`, such as gVisor, have not been verified: mailroll does not know whether they give each sandbox its own boot id and PID namespace identity, so treat lock recovery there as unsupported and give each sandbox that shares a folder its own host name.
  - On macOS and Windows the process space adds nothing to the host name, so two machines with the same host name that share a folder, such as two Macs on an SMB or iCloud folder, cloned Windows virtual machines, or Windows containers with process isolation, are not told apart: each can take over the live lock of the other, and both send. Give each of them its own host name.
  - Only runs of this version record and check the process space. A run of mailroll 0.1, or of any version before this one, that shares the folder still recovers a lock by host name and process id alone, so it can take over the lock of a run in another container with the same host name. The protection holds only once every run that shares the folder is upgraded.
- **A run that lost its lock.** The ownership checks narrow, but do not remove, the chance that a run whose lock was deleted, and that the operating system suspended at the wrong moment (sleep, Ctrl-Z or SIGSTOP, a debugger, a frozen virtual machine), overwrites the history of the run that took the list over. The setups mailroll does not support are listed in [Locks](/guides/history#locks).
- **Size.** mailroll reads a list's history into memory in one piece, and the evidence fields have no length limit. A history larger than what Node.js can hold in a single string (about 512 MiB in current 64-bit releases; it depends on the Node.js version) cannot be loaded.
- **Attempt ids from your own generator.** mailroll checks that an id is not repeated within one list of a run and is not already in the recipient's entry. It cannot detect a repetition across lists or across runs.

## Previews

A dry run with previews writes every rendered message to an HTML file instead of sending it. Previews are written by `mailroll send --mode dry-run --write-previews` (folder `--previews-dir`, default `previews`), by the menu's QA step (always `previews`), and by the SDK when you pass `previewDir` in dry-run mode.

### Paths and names

Each list gets its own folder:

```text Preview layout wrap
<previews>/<template folder>/<state stem>/<NNNN>-<address>.html
```

- `<template folder>` is the template id with every run of characters other than ASCII letters and digits replaced by `_`, and leading and trailing `_` removed.
- `<state stem>` is the same stem as the list's [state files](#names).
- `<NNNN>` is a four-digit counter in the order messages are rendered, starting at `0001`.
- `<address>` is the recipient address with every character other than letters `a`–`z` and `A`–`Z`, digits, `.`, `_`, `@` and `-` replaced by `_`. A name longer than 80 characters is cut to 80 and followed by `~` and the first 10 hexadecimal characters of the address's SHA-256 hash, so long names stay distinct.

For example, `previews/welcome/recipients/0001-ana@example.com.html`. Two lists that would share a preview folder are rejected before anything is rendered.

### Contents

Each file starts with one comment line that summarizes the message, followed by the rendered HTML:

```html previews/welcome/recipients/0001-ana@example.com.html wrap
<!-- DRY RUN preview | to: ana@example.com | cc: records@example.com | subject: Welcome to Acme -->
```

The `cc:` part appears only when the message has a CC. Any `<` and `>` in these values are removed so the comment stays intact.

### Lifecycle and permissions

Right before a list is rendered, mailroll deletes that list's preview folder with everything in it, so the folder always shows exactly the last run. Folders of other lists are not touched. Do not keep your own files in a preview folder.

Preview folders are created with permissions `0700` and files with `0600`. Previews contain your recipients' data; keep them out of version control and delete them when you are done. They are always safe to delete.

## Token cache

When a connection signs in to Microsoft, the sign-in is saved so later runs, including non-interactive ones, can reuse it.

### Path

```text Token cache path wrap
<TOKEN_CACHE_PATH or .secrets/tokens>/<campaign key>/<connection key>.json
```

The keys are the campaign id and connection id with every run of characters other than ASCII letters and digits replaced by `_`, and leading and trailing `_` removed. Letter case is kept. Campaign `acme/onboarding` and connection `outlook-1` use `.secrets/tokens/acme_onboarding/outlook_1.json`. The root is relative to the current working directory unless `TOKEN_CACHE_PATH` is absolute; see [TOKEN_CACHE_PATH](/reference/environment).

`mailroll send` and `mailroll-outlook export-sent` share the same file for a connection.

### Writes and permissions

mailroll writes the cache only when the sign-in data changed. When the cache folder does not exist yet, it creates it and flushes the parent of every folder level it created. It then writes a temporary file and flushes it to disk, renames it over the cache, and flushes the folder, so a crash never leaves a half-written cache and a saved sign-in survives a power failure. On Windows a folder flush is skipped when Windows refuses it, as for the send state; see [Platforms and limits](#platforms-and-limits). If the rename fails, the temporary file is removed and the previous cache stays in place. The folder is created with permissions `0700` and the file is set to `0600`.

<Warning>
  The token cache lets whoever holds it act as the signed-in mailbox, within the permissions your Entra app was granted, until the tokens expire or are revoked. Keep `.secrets/` out of version control, backups you share, and container images.
</Warning>

### Damaged or deleted cache

A cache file that cannot be parsed is ignored with this notice, and you are asked to sign in again:

```text Output wrap
Token cache .secrets/tokens/acme_onboarding/outlook_1.json is unreadable (…); ignoring it — you will be asked to sign in again.
```

The notice goes to stderr in the CLI, and to `onSignInMessage` in the SDK when you set it. Deleting the cache is always safe and behaves the same way: the next test or live send, or `mailroll-outlook export-sent`, needs a new sign-in. In an interactive terminal that is a device-code sign-in. Without a terminal, or with `signIn: 'cached-only'` in the SDK, the run fails with `SignInRequiredError` instead. See [Sign in](/guides/outlook#sign-in).

## Sent Items export

`mailroll-outlook export-sent` writes the messages found in a connection's Sent Items to the file named by `-o`/`--out`.

- The file must not exist yet. mailroll creates it exclusively, so it never overwrites anything; an existing file fails with `cannot create <file> (it must not exist yet)`.
- It is created only after every page was fetched from Microsoft Graph, with permissions `0600`.

The file is one JSON object, written with two-space indentation. This illustrative export holds a single message:

```json sent-items.json
{
  "exportedAt": "2026-01-16T08:30:00.000Z",
  "campaignId": "acme/onboarding",
  "connectionId": "outlook-1",
  "mailbox": "sender@example.com",
  "since": "2026-01-15T00:00:00.000Z",
  "count": 1,
  "messages": [
    {
      "subject": "Welcome to Acme",
      "to": ["cleo@example.com"],
      "cc": [],
      "sentAt": "2026-01-15T10:02:04Z"
    }
  ]
}
```

It contains subjects and recipient addresses, so store it like the rest of your recipient data. How to use it to check uncertain sends is covered in [Export Sent Items](/guides/export-sent).

## Integrations

`mailroll.json` sits next to the `package.json` of the project that installs mailroll, and lists the integrations to activate. It is yours: mailroll only reads it, and only when you send.

```json mailroll.json
{ "integrations": ["acme-mailroll-sender"] }
```

`integrations` is the only field, besides an optional `$schema`. Each entry names an installed package, or a subpath it exports, and appears once. Any other field, a relative path or a URL is an error.

When the list is not empty, mailroll keeps a helper file at `node_modules/.cache/mailroll/import.mjs` in that project, and loads the integrations through it so they resolve from your project. Its content never changes: mailroll writes it on the first run (to a temporary file that it then renames, so simultaneous runs never see a half-written file), rewrites it only if its content was changed, and otherwise only reads it. It is safe to delete; the next send recreates it. How the whole check works is covered in [Add an integration](/guides/integrations).
